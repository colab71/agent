**问题判断**

异常文件里的核心报错是 `AuthorizationDeniedException: Access Denied`，随后又出现 `Unable to handle the Spring Security Exception because the response is already committed.`。这说明 stream 接口的数据库插入已经完成，SSE 响应也已经开始提交；之后 Servlet async/error dispatch 又进入 Spring Security 过滤链，但没有正常的 JWT 认证上下文，于是被 `.anyRequest().authenticated()` 拦截，响应已经提交后无法再返回普通错误响应，就产生了现在的二次异常。

相关位置：
- `E:\ai\新建 文本文档.txt:3`：`AuthorizationDeniedException`
- `E:\ai\新建 文本文档.txt:80`：响应已提交后无法处理 Spring Security 异常
- `ai-springboot/src/main/java/com/example/aispringboot/config/SecurityConfig.java:56`：所有非公开路径都要求认证
- `ai-springboot/src/main/java/com/example/aispringboot/controller/PsychologicalChatController.java:45`：`POST /api/psychological-chat/stream` 返回 SSE 流
- `ai-springboot/src/main/java/com/example/aispringboot/AiService/impl/PsychologicalSupportServiceImpl.java:102`：用户消息先保存到数据库

**实施计划**

1. 修改 `SecurityConfig`，显式放行 Servlet 的 `ASYNC` 和 `ERROR` dispatcher。
   - 初始的 `/api/psychological-chat/stream` 请求仍然要求 JWT。
   - 只放行同一次请求后续的异步派发和错误派发，避免 SSE 已开始输出后被 Security 二次拦截。
   - 需要引入 `jakarta.servlet.DispatcherType`。

2. 同时把 `/error` 加入公开路径，避免 Spring Boot 默认错误端点在错误派发过程中再次被 JWT 过滤器拦截。
   - 这是 Spring Security + Spring Boot error endpoint 的常规配置。
   - 不会让业务接口免登录；只影响默认错误处理入口。

3. 给 stream Controller 增加 SSE 级别的异常兜底。
   - 在 `PsychologicalChatController.streamChat` 的返回流上加 `onErrorResume`。
   - 如果 AI 服务、sessionId 格式、网络调用等在流式过程中报错，返回一个 `event: error` 的 SSE 事件，然后结束流。
   - 这样前端能收到结构化错误，而不是连接直接中断或触发 `/error`。

4. 暂不重构 `PsychologicalSupportServiceImpl` 里的 `Flux.create(...).subscribe()`。
   - 这里确实有可改进点：取消订阅和 backpressure 处理不够干净。
   - 但本次异常的直接根因是 Security 对 async/error dispatch 的拦截；先做低风险修复，避免引入额外行为变化。

   - 如果你允许，再运行测试或启动项目复测 `/api/psychological-chat/stream`，观察是否还出现 `AuthorizationDeniedException` 和 `response is already committed`。
